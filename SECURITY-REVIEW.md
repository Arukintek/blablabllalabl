# Security review summary

## Executive summary
This project was reviewed for authentication, authorization, API exposure, session handling, deployment configuration, and production hardening. Several issues were identified and addressed in the codebase. The project is still not fully production-hardened, but the critical and high-risk problems around server-side authorization and secret handling have been reduced significantly.

## Work completed
- Removed the hardcoded session-secret fallback; startup now requires `SESSION_SECRET`.
- Hardened session cookies with `HttpOnly`, `SameSite=Lax`, and `Secure` in production; guarded signed-cookie comparison against malformed signatures.
- Restricted CORS and state-changing request origins; production requires exact HTTPS origins via `CORS_ORIGIN`.
- Added login rate limiting (10 attempts per IP per 15 minutes), production HSTS, and structured HTTP request logs that omit query values, request bodies, and IP addresses.
- Added `SESSION_SECRET` and `CORS_ORIGIN` as Render environment variables to configure.
- Removed the client-side demo-login fallback, which could send users into protected dashboards without a valid server session.
- Updated demo seeding to store bcrypt-hashed passwords rather than plaintext.
- After owner authorization, replaced the existing demo administrator credential in the configured database with a bcrypt-hashed password; the password itself is not stored in this report or repository.
- Added `express-rate-limit` and ran a production dependency audit. It reported three high-severity Prisma-related advisories; the suggested Prisma 7 upgrade is not applied pending compatibility review.

## Validation completed
- `node --check backend/server.js` and `node --check backend/src/routes/auth.js` passed.
- `node --check js/login.js` and `node --check backend/prisma/seed-demo.js` passed.
- Verified that the administrator can authenticate through the local API after the authorized password reset (HTTP 200).
- Production startup configuration was smoke-tested: missing `CORS_ORIGIN` is rejected and a valid HTTPS origin is accepted.
- `git diff --check` passed.
- No full end-to-end tests against a production deployment were run.

## Findings addressed

### 1) Hardcoded session secret fallback
Status: Fixed

- The original implementation used a hardcoded fallback secret when `SESSION_SECRET` was missing.
- This was removed, and the application now fails fast if the secret is not configured.
- The environment configuration in `render.yaml` now includes `SESSION_SECRET` as a required variable.

### 2) Weak or missing cookie protections in production
Status: Fixed for the current deployment posture

- Session cookies now include `HttpOnly` and `SameSite=Lax`.
- In production, `Secure` is added to cookies, which prevents transmission over plaintext HTTP.

### 3) Unrestricted CORS policy
Status: Fixed

- `app.use(cors())` was replaced with a restricted allowlist configuration.
- Only explicit origins are allowed, and credentials are enabled only for those trusted origins.

### 4) Brute-force login exposure
Status: Fixed

- Added rate limiting for `/api/auth/login` to reduce password spraying and brute-force attempts.
- This is a critical hardening step for a public or semi-public deployment.

### 5) Signed session validation weakness
Status: Fixed

- The signed-session verification logic now checks output length before calling `timingSafeEqual`, preventing malformed or malicious cookie payloads from being treated as valid input.

## Current risk status
The highest-risk issues have been reduced, but the project should still be treated as a demo-grade deployment until the following production hardening checklist is completed.

## Production hardening checklist

### Environment and secrets
- [ ] Define `SESSION_SECRET` as a long random value generated by a secure source.
- [ ] Keep secrets out of source control and commit history.
- [ ] Use separate secrets for development, staging, and production.
- [ ] Rotate credentials if any secret was previously exposed.
- [ ] Keep `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, and `DEMO_PASSWORD` in platform environment variables, not in code.

### HTTP and cookie security
- [x] Configure the Render service to use HTTPS; cookies set in production include `Secure`.
- [x] Require exact HTTPS origins through `CORS_ORIGIN` in production and reject missing or malformed allowlists at startup.
- [x] Add HSTS on HTTPS production requests.
- [ ] Consider CSRF protection for any non-GET state-changing endpoints if the app is used from a browser with cross-site requests.

### Authentication and authorization
- [x] Rate-limit login attempts per client IP.
- [ ] Add account lockout or exponential backoff for repeated failed logins.
- [x] Emit structured request logs with a request ID, method, path, status, and duration; logs deliberately omit request bodies, query values, and IP addresses.
- [ ] Review admin-only routes and ensure each action checks the user’s role and/or ownership server-side.

### Data and dependency hygiene
- [x] Ran `npm audit --omit=dev`; it reported three high-severity Prisma-related advisories (including the Prisma CLI and transitive packages).
- [ ] Upgrade Prisma after reviewing the breaking changes and validating schema generation, migrations, and runtime compatibility; npm reports the available fix as Prisma 7.x, a major-version upgrade.
- [ ] Keep Prisma and runtime dependencies up to date.
- [ ] Validate all user-provided values before database writes.
- [ ] Review and limit returned JSON payloads so sensitive fields are never exposed to unauthorized roles.

### Deployment safety
- [ ] Do not expose debug routes or admin tools in public production environments.
- [ ] Use a production-grade database and disable demo seeding in live environments.
- [ ] Configure server logs without leaking personal data or credentials.
- [ ] Restrict admin access to trusted networks or identity-managed access.

## Safe `.env` / deployment guidance
Example variable names and purpose:

```env
SESSION_SECRET=replace-with-a-strong-random-secret
DATABASE_URL=postgresql://user:password@host:5432/dbname
DATABASE_URL_UNPOOLED=postgresql://user:password@host:5432/dbname
DEMO_PASSWORD=generate-a-strong-password-only-for-demo-seeding
NODE_ENV=production
CORS_ORIGIN=https://your-render-service.onrender.com
PORT=5000
```

Important:
- never commit `.env` files
- use platform secrets or vault-managed environment variables
- verify that all secrets are loaded only from the runtime environment
- set `CORS_ORIGIN` to the exact public frontend origin(s), without a trailing slash or path; configure the same value in Render
- rotate `SESSION_SECRET` and database credentials in the hosting provider if they were ever exposed; changing `SESSION_SECRET` invalidates existing sessions
- use a unique, cryptographically generated `SESSION_SECRET` for each environment

## Dependency audit details
`npm audit --omit=dev` reported three high-severity Prisma advisories for the installed Prisma 6.19.3 dependency tree (`prisma`, `@prisma/config`, and `deepmerge-ts`). npm suggests Prisma 7.x as the available fix. This major upgrade was not applied automatically because it needs compatibility testing and may require migration/configuration changes.

## Final assessment
The project no longer contains the most obvious severe issues previously identified, especially around hardcoded session secrets and unrestricted admin access. However, it should still be treated as a demo project until all checklist items above are applied in a real production environment.

Before deploying, set a unique random `SESSION_SECRET` and the exact public HTTPS `CORS_ORIGIN` in Render. Rotate any credentials that may have been exposed. Review the Prisma advisories and test a compatible upgrade before treating the dependency audit as resolved.
